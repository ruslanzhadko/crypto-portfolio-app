## 1. Что расходовало Neon (решено 20.10)

Free-лимиты (100 CU·ч и 5 ГБ egress на проект) исчерпал круглосуточный опрос БД биржевым
worker (минимум 6 CU·ч в сутки), частые снимки капитала, чтения истории и опрос из браузера.
Решение — §3: worker в режимах «активный / простой», окна :00/:30, healthcheck без SQL,
облегчённые запросы, CDN-кэш фото.

## 3. Целевая архитектура: «горячее состояние — в worker, БД — для хранения и UI»

Главный принцип: **процессы, которые работают постоянно, не должны постоянно
обращаться к PostgreSQL.** Частые данные живут в памяти фонового сервиса на VPS; в БД
пишется то, что нужно UI и истории, — пачками и в общих «окнах пробуждения».

```text
Браузер ──15 с, пока вкладка активна──► Vercel API ──► Neon (UI-модель данных)
                                            │
                                            └─ отметка «пользователь смотрит» в Vercel
                                               Runtime Cache (не чаще 1 раза в минуту)
                                                    ▲ worker опрашивает каждые 10 с
VPS: background service ── REST/WebSocket ──► биржи, Telegram, цены
     • в памяти: позиции, mark-цены, правила оповещений, буфер постов
     • в БД: активный режим — как сейчас; простой — одно окно раз в 30 мин;
       события (сработал триггер, ликвидация близко) — сразу
```

### 3.1 Режимы worker

| Режим | Когда | Поведение |
| --- | --- | --- |
| Активный | Пользователь открыл страницы бирж/позиций/дашборда в последние ~10 минут, или нажал «Обновить» | Как сейчас: позиции ~30 с, балансы ~2 мин. БД и так бодрствует из-за опроса браузера |
| Простой | Никто не смотрит | Полная синхронизация всех подключений **раз в 30 минут**, затем закрыть соединения Prisma и не трогать БД до следующего окна |
| Событие | Сработало правило (в будущем: ликвидация близко, исполнен ордер) | Сразу отправить уведомление в Telegram и записать событие |

**Реализовано 20.10.2026**, работает в production:

- Сигнал: API бирж/дашборда/кошельков отмечают пользователя в Vercel Runtime Cache
  (`lib/exchanges/activity.ts`, не чаще раза в минуту, срок 10 минут). Worker раз в 10 с
  читает `GET /api/worker/activity` (Bearer `EXCHANGE_WORKER_SIGNAL_SECRET`, для защищённого
  Preview — `EXCHANGE_ACTIVITY_BYPASS`). Входящие порты на VM не нужны. Первоначальный
  вариант с HMAC-push через Cloudflare Tunnel отложен до живого канала (§3.4).
- Появившемуся зрителю задания переносятся на «сейчас» (кроме заданий в backoff).
- В простое — одно окно в :00/:30: heartbeat с долгим сроком, обслуживание, все задания,
  снимки капитала, затем `prisma.$disconnect()`. Между окнами — 0 SQL-запросов (замер на
  локальном PostgreSQL с логированием всех запросов).
- Docker healthcheck читает локальный файл `/app/.worker-run/alive` (раньше —
  SQL каждые 30 с, что само держало Neon включённым).
- Сразу после прихода зрителя (2 мин) данные последнего окна не помечаются устаревшими.
- Снимки капитала объединяются (не чаще раза в 2,5 мин на пользователя); история капитала
  прореживается в SQL (≤ ~720 точек, без JSON `sources`), опрос истории — раз в 5 мин;
  overview читает только нужные столбцы; забытая вкладка перестаёт опрашивать через 30 мин
  без действий; фото ленты кэшируются CDN (7 дней), ответ 304 не читает байты из БД.
- Без настроенных переменных worker работает по-старому (быстро для всех).

  сам опрашивает каналы (`getMessages` с `minId`): раз в 10 с, пока лента открыта, иначе раз в окно.

### 3.4 Живой режим на странице: секунды, а не 30 секунд

Требование: пока пользователь смотрит позиции, цены, триггеры или ленту — данные должны
обновляться как можно быстрее; в фоне допустимо раз в 30–60 минут.

Если просто чаще опрашивать Vercel → Neon, растут egress и нагрузка, а быстрее 5–15 секунд
это всё равно не станет. Поэтому живые данные идут **напрямую с VPS в браузер, минуя БД**:

```text
Биржи (WebSocket: позиции, mark-цены, тикеры)  ─┐
Telegram listener (новые посты)                  ├─► VPS: состояние в памяти
Цены для триггеров (WebSocket бирж)              ─┘        │ SSE / WebSocket
                                                            ▼ (через Cloudflare Tunnel, HTTPS)
Браузер ◄── первая загрузка страницы: Vercel → Neon     браузер, задержка ~1 с
```

- Vercel выдаёт браузеру короткоживущий подписанный токен (JWT: `userId`, срок ~5 мин);
  VPS проверяет подпись общим секретом и отдаёт только данные этого пользователя.
- Позиции: приватные WebSocket-потоки бирж там, где они есть; иначе REST-опрос каждые
  2–5 с **только пока открыта страница** (в пределах лимитов бирж). Mark-цена и PnL —
  из публичных потоков каждую секунду.
- Лента: listener сразу отправляет новый пост открытым вкладкам; в БД пишет сразу, если
  кто-то читает, иначе пачкой в окне.
- Если живой канал недоступен, страница откатывается на текущий опрос Vercel → Neon.
- Для Neon это почти бесплатно: БД нужна для первой загрузки страницы и периодических
  снимков, а не для каждого обновления.

**Ценовые триггеры в реальном времени.** `PriceTrigger.tokenId` — это CoinGecko ID. Для
монет, торгующихся на биржах, — сопоставление CoinGecko ID → пара USDT (проверяется
сравнением цены, неоднозначные не сопоставляются) и проверка по потоку тикеров каждую
секунду. Остальные монеты — один пакетный запрос CoinGecko на все ID раз в 5 минут:
Demo-план — 10 000 запросов в месяц (по сторонним источникам), 8 640 в месяц укладываются.
Уведомление в Telegram отправляется с VPS сразу; в БД пишется срабатывание.

3. **Как тестировать без отдельной базы:**
   - разработка — локальный PostgreSQL из `docker-compose.yml` (бесплатно, без лимитов);
     публичные источники (Hyperliquid, Aster по адресу) работают с любого IP;
   - биржевые функции на реальных ключах — в production с флагом пилота
     (`EXCHANGES_PILOT_USER_IDS` = список допущенных пользователей); интеграции read-only;
   - рискованные изменения схемы — **временная ветка Neon от production** (копия данных,
     в Free до 10 веток, тратит общий лимит только пока используется), удаляется после
     проверки. В её строке подключения не запускать постоянный worker без режима простоя.
4. Резервные копии production: ежедневный `pg_dump` с VPS в бесплатное объектное хранилище
   (Cloudflare R2 10 ГБ / Backblaze B2) — на Free история восстановления Neon лишь 6 часов.

Если когда-то снова понадобится постоянное тестовое окружение — второй проект Neon Free
(свои 100 CU·ч, $0) или PostgreSQL-контейнер на том же VPS.

Когда стоит переходить на «полноценную» БД: если данные перерастут ~0,5–1 ГБ, понадобится
постоянная запись (например, хранение тиков/свечей для аналитики) или нагрузка многих
пользователей. Варианты тогда: Neon Launch с отключённым засыпанием (~$19+/мес за 0,25 CU),
Supabase Pro ($25/мес), либо PostgreSQL на том же VPS (дёшево, но бэкапы, обновления и
безопасность становятся вашей ответственностью; Vercel-функциям тогда нужен TLS-доступ
к БД и пул соединений, например PgBouncer). Код зависит только от `DATABASE_URL` /
`DIRECT_URL`, поэтому смена провайдера — это миграция данных и переменных окружения.

## 5. Переезд с GCP (бесплатный период закончится примерно в январе 2027)

Пошаговая инструкция — [MIGRATIONS.md](MIGRATIONS.md) §6. Ниже — соображения и выбор страны.

Worker уже работает в Docker (`Dockerfile.exchanges`) и деплоится через GitHub Actions по
SSH (`.github/workflows/worker-deploy.yml`, `deploy/`). Для быстрого переезда:

- Параметризовать установочные скрипты: сейчас `install-worker-actions.sh` и
  `install-worker-update.sh` ожидают именно `exchange-dev.env` и пользователя `rzhadko`.
- Добавить Telegram listener и туннель сигналов в тот же Docker Compose, чтобы новая VM
  поднималась одной командой.
- **Главная боль переезда — смена исходящего IP:** у каждой биржи нужно обновить IP
  whitelist read-only ключа, у Aster — список IP API Wallet. Выбирать провайдера, где IP
  можно сохранить при пересоздании сервера (например, Primary IP у Hetzner), и обновлять
  `EXCHANGE_WORKER_PUBLIC_IP`. Переезд планировать заранее: на время смены ключей
  подключения будут в ошибке.
- GCP Always Free (e2-micro) доступен только в регионах США: Binance и Bybit блокируют
  американские IP, поэтому для worker он не подходит.

### Выбор страны VPS

Геоблокировки бирж бывают двух видов: по **стране аккаунта (KYC)** и по **IP сервера**.
Для worker важна вторая: Binance отвечает `451 restricted location`, Bybit и другие — `403`
от CDN, причём обычно на любой запрос, включая публичные. Сведения из обзоров (октябрь 2026,
не официальные списки — проверять на сайтах бирж):

- **США** — блокируют Binance, Bybit, OKX global, MEXC и многие другие. Исключить.
- **ЕС после MiCA (с 1 июля 2026)** — нелицензированные биржи ограничивают ЕС: Bitget
  блокирует Германию, MEXC уходит из Нидерландов (до 16.11.2026), BingX ограничивает
  Нидерланды, Binance по ряду источников прекратила услуги в ЕС. Нидерланды и Германия —
  рискованный выбор. Текущий GCP в Варшаве пока работает со всеми подключёнными биржами,
  но регуляторная обстановка в ЕС может измениться.
- **Сингапур, Гонконг, Канада** — в списках ограничений Bybit/OKX/Bitget. Исключить.
- Кандидаты вне ЕС с доступными VPS: Великобритания (Bybit вернулся в декабре 2025, но
  Binance ограничивает), Швейцария, Сербия, Молдова, Грузия, Турция, ОАЭ (большинство бирж
  лицензированы или работают в Дубае). Ни один вариант не гарантирован навсегда.

**Украина как основная площадка (предложение пользователя, 19.10.2026).** Плюсы: все
используемые биржи обслуживают Украину (исключены только оккупированные регионы), ключи и
KYC пользователя украинские, большинство будущих пользователей в Украине — живой канал
(§3.4) будет для них с минимальной задержкой; цены VPS умеренные, оплата в гривне. Минусы:
перебои электроэнергии и связи, возможные атаки на инфраструктуру. Требования к провайдеру:
ЦОД в Киеве с ДБЖ и дизель-генераторами (уточнить запас топлива), несколько аплинков, SLA,
KVM, фиксированный IPv4. Спросить провайдера прямо: адрес ЦОД, автономность, история
простоев 2022–2025. Задержка до серверов бирж (Токио/Сингапур/Франкфурт) для мониторинга
некритична.

**Резерв.** Практически все биржи позволяют несколько IP в whitelist ключа (Aster — в
списке API Wallet). Поэтому в ключи заранее вносятся **оба** IP: основной (Украина) и
резервный (ЕС или другая страна, проверенная пробой). Переключение — запуск того же
Docker-образа на резерве, без замены ключей. Резерв держать «тёплым», без постоянной
работы с БД; решение о переключении — по HTTP-проверке основного, а не по опросу Neon.
До окончания пробного периода GCP резервом может быть текущая VM в Варшаве; потом —
дешёвый VPS за ~€4–5. Итого инфраструктура: Украина ~$5–12 + резерв ~€4–5 + Neon $0–8.

Порядок выбора: арендовать почасовую VM в 2–3 кандидатах (центы за час), запустить
`node scripts/exchange-geo-probe.mjs` (публичные endpoint всех бирж, без ключей), выбрать
страну, где всё `OK`, затем после переезда проверить один read-only ключ. Скрипт
периодически запускать и на рабочем VPS — он заранее покажет новую блокировку.

## 6. Хранение данных

База 83 МБ (25.10, после удаления `PriceHistory`: 57 МБ, 303 831 строка за 14.06–01.10, бэкап в папке
бэкапов, `docs/private/`). Размеры на 1 октября: `TelegramFeedMedia` ~19 МБ (106 фото), `NotificationLog` ~5 МБ
(из 20 941 записи 20 301 — `failed`, старые ошибки без причины), `PortfolioSnapshot` ~5 МБ.

| Таблица | Возможное решение | Что теряется |
| --- | --- | --- |
| `NotificationLog` | Срок хранения ~90 дней | Старая история уведомлений |
| `TelegramFeedPost` / `TelegramFeedMedia` | **Решено 25.10:** хранить 30 дней (можно 14), чистить старше раз в сутки в окне listener | Старые посты/фото (удаление поста каскадно удаляет фото) |
| `PortfolioSnapshot`, `PortfolioCapitalSnapshot` | Сохранять 5-минутные точки за 7–30 дней, старше — часовые/дневные агрегаты | Детализация старой истории |
| `User`, `Wallet`, `TokenBalance`, `PriceTrigger`, биржевые таблицы | Не чистить без отдельного анализа | Доступ и текущие данные |

Перед любым удалением: резервная копия, количество строк и размер, удаление небольшими
партиями. Не использовать `scripts/reset-token-data.ts` — он удаляет данные полностью.
Очистка таблиц **не возвращает** уже израсходованные CU·ч. Проверка размеров (только чтение):

```sql
SELECT relname AS table_name,
       pg_size_pretty(pg_total_relation_size(relid)) AS total_size
FROM pg_stat_user_tables
ORDER BY pg_total_relation_size(relid) DESC;
```

## 9. Критерии готовности

- Тесты идут локально (одноразовый PostgreSQL в Docker), на пилоте в production или во временных
  ветках Neon.
- В простое на графике Neon видны длинные периоды `Endpoint inactive`; прогноз CU·ч и
  egress на месяц укладывается в лимит Free (или в выбранный бюджет Launch) с запасом.
- Позиции и балансы обновляются раз в 30 минут без зрителей и каждые ~30 секунд при
  открытой странице; ценовые оповещения приходят не позже, чем сейчас.
- Worker, listener и туннель разворачиваются на новой VM по инструкции за один вечер.
