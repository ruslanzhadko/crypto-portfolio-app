# Переносы, настройка и экономия — инструкции

Создано 20 октября 2026 года. Здесь собраны пошаговые инструкции для всех запланированных
переносов и настроек: что делать, в каком порядке, как проверить и как откатить. Почему
выбрана именно такая схема (причины расхода, архитектура, цены) — в
[INFRASTRUCTURE.md](INFRASTRUCTURE.md). Выпуск бирж в production подробно — в
[EXCHANGES_HANDOFF.md](EXCHANGES_HANDOFF.md) §8.

Общие правила для любого переноса:

- Сначала резервная копия и проверка способа восстановления, потом изменения.
- Секреты не печатать в чат, логи и Git; переносить через защищённые файлы/панели.
- Переносить код и схему, а не подменять рабочую БД тестовой.
- Каждое изменение проверять по факту (свежая синхронизация, ответ БД, график Neon), а не
  только по зелёному CI.

Правила: keyring шифрования (`EXCHANGE_ENCRYPTION_KEYS`) у сайта и worker одного окружения
одинаковый и никогда не хранится в БД; старые версии ключа не удалять, пока ими что-то
зашифровано. Секрет сигнала одинаковый в Vercel и в env worker. Ротация секрета сигнала:
новый в Vercel → redeploy → новый в env worker → пересоздать контейнер (см. §6.4).

## 3. Neon: возврат на Free 1 ноября

Решение принимается по замерам, а не заранее.

1. После 28.10 открыть Neon → проект → **Monitoring** за последние 3–7 дней: CU·ч в сутки и
   network transfer. Ориентир для Free: в среднем ≤ 2–2,5 CU·ч/сутки на весь проект
   (лимит 100 CU·ч/месяц) и egress заметно меньше 5 ГБ/месяц.
2. Если укладываемся: Billing → **Change plan** → Free. Перед этим убедиться, что в
   организации ≤ 10 веток на проект и хранение ≤ 1 ГБ на проект.
3. Если не укладываемся: остаться на Launch, оставить compute 0,25 CU и уведомление о тратах;
   ожидаемо $3–8/мес.
4. Второй проект организации на Launch тоже тарифицируется. До решения — ограничить его
   compute 0,25 CU и оставить засыпание.

**Разделение организаций**, если Launch нужен надолго, а второй проект должен остаться
бесплатным: создать новую организацию на Launch, перенести туда `cryptoportfolio` (Settings →
General → Transfer project; строки подключения не меняются; перед переносом снять интеграции
проекта), старую организацию перевести на Free. Обратный перенос Launch → Free Neon не
разрешает: тариф целевой организации должен быть не ниже исходной.

## 4. Выпуск бирж в production (этап C)

Подробности, переменные и откат — EXCHANGES_HANDOFF.md §8. Кратко:

1. Neon: создать ветку-копию от `production` (точка отката).
2. Проверить хост в строке подключения (production), прочитать `prisma/exchanges.sql`,
   выполнить `node --import tsx scripts/upgrade-exchanges.ts` с явно заданными
   production `DATABASE_URL`/`DIRECT_URL` (не через `.env`). Проверить таблицы и индексы.
3. Vercel Production: `EXCHANGES_ENABLED=true`, `EXCHANGES_PILOT_USER_IDS=<id владельца в
   production>`, `EXCHANGE_ENCRYPTION_KEYS`, `EXCHANGE_ENCRYPTION_KEY_VERSION`,
   `EXCHANGE_FINGERPRINT_KEY`, `EXCHANGE_WORKER_PUBLIC_IP`, `EXCHANGE_WORKER_SIGNAL_SECRET`.
4. Merge `develop` → `main`. Дождаться и Vercel, и GitHub Actions.
5. Worker: env с production-БД, `EXCHANGE_ACTIVITY_URL=https://crypto-portfolio-app-cyan.vercel.app/api/worker/activity`
   (production без защиты — `EXCHANGE_ACTIVITY_BYPASS` не нужен), автодеплой из `main`.
   Решить: отдельный production-контейнер на той же VM (нужна параметризация установщиков,
   §6.2) или переключение текущего контейнера на `main` — второе проще, раз тестовой базы
   больше не будет.
6. Заново подключить ключи бирж в production-интерфейсе, дождаться свежей синхронизации и
   сверить с биржами.
7. Удалить `exchange-dev`, удалить переопределения Preview для `develop` и Protection Bypass
   для preview (если не нужен). Отключить автоматические preview-деплои
   (`git.deploymentEnabled` в `vercel.json`) или убрать переменные БД из Preview.

## 5. Telegram listener: Render → VM (этап E1)

1. На VM создать env-файл listener (права 600): `DATABASE_URL`, `TELEGRAM_API_ID`,
   `TELEGRAM_API_HASH`, `TELEGRAM_USER_SESSION` — значения из Render.
2. Добавить образ/сервис listener (Dockerfile или общий Docker Compose с worker) и
   автодеплой из `main`, по образцу `Dockerfile.exchanges` и `deploy/worker-update.sh`.
3. **Одновременно может работать только один listener с этой сессией**: сначала остановить
   сервис на Render (Suspend), затем запустить на VM. Проверить логи и что новые посты
   появляются в ленте.
4. Через несколько дней без проблем удалить сервис на Render, чтобы не начислялась оплата.
5. Следующий шаг экономии: буферизовать посты и писать их в окна worker, а при открытой
   ленте — сразу (INFRASTRUCTURE.md §3.2).

## 6. Переезд VM: GCP → платный VPS (этап E2, декабрь)

### 6.1 Выбор

1. Кандидаты: Варшава (текущая страна, все биржи работают), Украина (основная аудитория,
   все биржи обслуживают Украину; риск перебоев электроэнергии). Германия и Нидерланды —
   рискованно из-за MiCA; США, Сингапур, Гонконг, Канада — исключить (INFRASTRUCTURE.md §5).
2. Требования: KVM, 2 vCPU / 2–4 ГБ RAM, 40 ГБ диск, фиксированный IPv4 (желательно
   переносимый между серверами), почасовая оплата для пробы, для Украины — ЦОД с
   ИБП и генераторами.
3. На пробной почасовой VM запустить `node scripts/exchange-geo-probe.mjs`: все строки `OK`.

### 6.2 Подготовка (до дня переезда)

1. Параметризовать `deploy/install-worker-actions.sh` и `deploy/install-worker-update.sh`
   (имя env-файла, пользователь, ветка) — сейчас они ожидают `exchange-dev.env` и `rzhadko`.
2. Собрать на новой VM: Docker, пользователь деплоя, root-owned
   `/usr/local/sbin/cryptoportfolio-worker-update`, env-файлы worker и listener (права 600),
   NTP. Проверить исходящий IP: `curl -s https://ipinfo.io/ip`.
3. **Добавить новый IP в whitelist каждого биржевого ключа рядом со старым** (биржи
   допускают несколько IP; у Aster — в списке IP API Wallet). Старый IP пока не удалять.
4. В GitHub Environment обновить `WORKER_HOST`, `WORKER_KNOWN_HOSTS` (host key сверять через
   консоль провайдера), при необходимости `WORKER_USER` и SSH-ключ.

### 6.3 День переезда

1. Остановить worker на GCP: `sudo docker stop cryptoportfolio-worker-dev` (или production-имя).
   Отключить там автообновление, чтобы push не запустил его снова.
2. Запустить worker на новой VM (ручной запуск скрипта деплоя или push в ветку).
3. Обновить `EXCHANGE_WORKER_PUBLIC_IP` в Vercel и env worker (это значение показывается в
   форме подключения), redeploy Vercel.
4. Проверить: healthcheck `healthy`; запросы `/api/worker/activity` идут с нового IP
   (`vercel logs requests`); свежая синхронизация каждой биржи без `IP_RESTRICTED`.
5. Перенести listener (§5) и, если уже сделаны, сервисы живого канала и триггеров.

### 6.4 После

- Через несколько дней удалить старый IP из whitelist ключей.
- В GCP удалить VM, диск, статический IP и снимки, чтобы после конца пробного периода ничего
  не начислялось. Проверить Billing GCP.
- Переменные из env-файла читаются только при создании контейнера: после правки env нужен
  новый деплой (новый коммит) или пересоздание контейнера тем же скриптом.

### 6.5 Откат

Старая VM не удаляется до подтверждения. Откат — `docker start` на старой VM, остановка
на новой, возврат `EXCHANGE_WORKER_PUBLIC_IP`. Ключи продолжают работать, потому что старый
IP остаётся в whitelist до конца проверки.

### 6.6 Резервный VPS (по желанию)

Второй дешёвый VPS в другой стране с тем же Docker-образом; его IP тоже в whitelist ключей.
Держать остановленным или «тёплым» без обращений к БД; переключение — запуск контейнера.
Одновременно активным должен быть только один worker (оба писали бы в одну БД).

## 7. Перенос БД (если когда-нибудь понадобится)

Когда стоит переходить: данные > ~1 ГБ, нужна постоянная запись (хранение свечей/тиков), рост
числа пользователей, при котором Neon бодрствует почти весь день (> ~$15/мес на Launch).

| Вариант | Стоимость | Плюсы | Минусы |
| --- | --- | --- | --- |
| Neon Launch без засыпания | ~$19+/мес за 0,25 CU | Ничего не переносить, PITR до 7 дней | Самый дорогой при круглосуточной работе |
| PostgreSQL на VPS | $0 сверху (VPS уже есть) | Без лимитов compute/egress | Бэкапы, обновления, безопасность, TLS и пул соединений (PgBouncer) на вас; Vercel-функции ходят к БД через интернет |
| Supabase Free / Pro | $0 (500 МБ, без бэкапов) / $25 | Всегда включена | Ещё один провайдер; лимиты Free |

Порядок переноса (любой вариант):

1. Поднять целевую БД той же мажорной версии PostgreSQL (сейчас 16), ограничить доступ
   (TLS, сильный пароль, firewall).
2. Окно обслуживания: остановить worker и listener, отключить cron.
3. `pg_dump --format=custom --no-owner` с `DIRECT_URL` (не pooler) → `pg_restore` в целевую БД.
4. Сверить число строк ключевых таблиц и размер; выполнить `/api/health?db=1` против новой БД.
5. Сменить `DATABASE_URL`/`DIRECT_URL` в Vercel (Production), env worker и listener;
   redeploy/пересоздать контейнеры.
6. Проверить вход, кошельки, ленту, биржи (свежая синхронизация).
7. Старую БД держать без изменений 1–2 недели как откат, потом удалить.

Зашифрованные биржевые ключи переносятся вместе с БД и продолжают расшифровываться: AAD
привязан к `userId`/`connectionId`, а они при `pg_dump` не меняются. Keyring шифрования не
менять одновременно с переносом.

## 8. Резервные копии

На Neon Free история восстановления — 6 часов, этого мало.

1. На VM — ежедневный cron/systemd timer: `pg_dump --format=custom` по `DIRECT_URL` (только
   чтение) → сжатие → загрузка в Cloudflare R2 (10 ГБ бесплатно) или Backblaze B2.
2. Хранить 7 ежедневных и 4 еженедельных копии.
3. Раз в месяц пробное восстановление в локальный PostgreSQL (`docker-compose.yml`).
4. Время запуска совместить с окном worker (:00 или :30), чтобы не будить Neon отдельно.

## 9. Резерв оптимизаций (ещё не сделано)

| Что | Эффект | Сложность |

| Триггеры и `update-prices` в worker, отключить cron-job.org (§3.2) | Neon будится реже; оповещения быстрее | Средняя |

| Очистка `PriceHistory`, срок хранения `NotificationLog`, агрегация старых снимков капитала (INFRASTRUCTURE.md §6) | −~70 МБ хранения | Низкая, после бэкапа |
| Фото ленты в R2 вместо `bytea` | Меньше размер БД и egress | Средняя |
| Живой канал (§3.4) и WebSocket бирж | Секундные обновления без нагрузки на БД | Высокая |
